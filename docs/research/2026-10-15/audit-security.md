# Code audit: security and abuse, once strangers can reach it

Audited 2026-10-15 against the repo as it stood then (free reproduction scripts, scratch databases, dummy keys). **Verification: independently verified (verdicts inline).** Durable copy of the agent's result (the raw journals are session-internal).

## Summary

Audited the repo for exposure to internet strangers under shape H (home PC behind a Cloudflare named tunnel) and shape C (cloud host behind a platform proxy). Reproductions are in scratchpad/audit/ (all isolated: cwd = scratch folder so the repo .env is never read, dummy non-empty keys set before importing app, DB_PATH on a throwaway file, no port bound, no paid calls). NOTE: the working tree is being edited live — not only app/config.py but also scripts/telegram_bot.py changed under me during the audit, and two issues I was mid-reporting (11.17 Settings-repr secret leak, and the Telegram token-in-logs leak) are now fixed in the current tree; I verified and recorded them as such (F11, F12) rather than as open.\n\nONE BLOCKER before any public URL: F1 — the 5/day cap is deployment-wide, so a single stranger from one IP can exhaust it in 5 trivial submissions and 429-lock the web page AND the bot for everyone until midnight IST (reproduced in repro_cap.py; acknowledged in PROJECT_PLAN §11 A). Money itself stays bounded (the cap holds; refunds only fire when nothing was spent), so there is no unbounded-spend hole — the blocker is cheap denial-of-service/lockout, which needs a real per-visitor limit + bot shield before go-live.\n\nClient-IP derivation (task a): under shape H the per-IP limiter sees the true visitor IP and XFF spoofing FAILS, because cloudflared's edge appends the real IP as the rightmost X-Forwarded-For entry and the installed uvicorn ProxyHeadersMiddleware (default trusted_hosts=127.0.0.1) takes the rightmost untrusted host (verified in repro_proxy.py). Under shape C it breaks (F2): every visitor collapses to the one proxy IP, and the reflex fix FORWARDED_ALLOW_IPS=* makes the per-IP limit fully spoofable (leftmost, client-controlled).\n\nShould-fix before inviting real users: F2 (IP attribution under C), F3 (/docs,/redoc,/openapi.json public — admin routes are correctly hidden from the schema), F4 (no rate limit/auth on read+SSE routes, no uvicorn concurrency cap → flood/connection-exhaustion DoS), F5 (25 MB body cap applied to JSON text/link routes; text field has no max_length and is parsed+regex-scanned before the quota), F6 (no CSP/nosniff/Referrer-Policy/framing headers — though index.html's own XSS defenses via esc()/md()/safeUrl() are strong), F7 (subtitle fetch skips the SSRF host allowlist and follows redirects — under H reaches the home LAN), F9 (bot answers anyone, §11 18). Nice-to-have: F8 (no authz on /reports and /stream, mitigated only by uuid4 ids), F10 (dashboard gate is sound under H but unreachable by the owner under C, with a narrow loopback-proxy exposure edge case), plus the two already-fixed items F11/F12 (F12 lacks a regression test). The dashboard local-only gate and the upload/body ASGI middleware are otherwise solid, and SSRF on the main link path (strict_host allowlist + pinned yt-dlp extractors) is well constructed apart from F7.

## Findings

### F1. One visitor can exhaust the deployment-wide 5/day cap and lock out everyone, from a single IP, for near-zero cost
*blocker · applies to: both · `app/api/limits.py:144` · tracked: 11.A (A-section narrative, not a numbered item)*

**Scenario.** The daily cap (max_checks_per_day=5, config.py:88) is deployment-wide and shared by the web page and the Telegram bot. A stranger submits 5 real text claims (each a few cents, 'hi'-style messages are refused free). The 6th submission from ANY other visitor gets HTTP 429 'reached its daily limit' until midnight IST. The per-IP hourly limit is 10 (config.py:78) — higher than the daily cap of 5 — so a single IP exhausts the global cap before the per-IP guard even bites. No multiple IPs, no spoofing, no botnet needed.

**Evidence.** scratchpad/audit/repro_cap.py (ran against the live limiter + a fresh scratch DB) printed: attacker 203.0.113.50 granted checks 1-5, then victims 198.51.100.2 and 198.51.100.3 both got 'HTTP 429: This service has reached its daily limit of 5 checks'; used_today=5. Acknowledged in PROJECT_PLAN §11 A ('the public would exhaust it in minutes, and then everyone is refused').

**Fix.** Before any public URL: add a real per-visitor budget (per-IP/day, and per phone-number on WhatsApp) that is much tighter than the deployment cap, plus a bot shield (Cloudflare Turnstile / sign-in) as §11 A anticipates; keep the deployment cap only as a spend backstop, and set a hard monthly limit in the Anthropic console. Consider separate reserved slots per surface so one abuser cannot starve the other.

**Verifier: reproduced.** Reproduced through the real HTTP routes and the real limiter. Script: C:\Users\VINAYA~1\AppData\Local\Temp\claude\c--Users-Vinayak-Mokashi-Python-Sab-Information-Verifier\4b88200f-d561-4246-b38d-1eac8cf3cade\scratchpad\audit\sv\v_f1.py, part A (engine stubbed, scratch DB, network blocked except loopback). Five DISTINCT text claims from 203.0.113.50 each returned 202. The victims 198.51.100.2 and 198.51.100.3 then got 429 'This service has reached its daily limit of 5 checks. It resets at midnight India time'. used_today=5. The per-IP limit (10/h) is higher than the cap (5/day), so it never bites first. Same under H and C, because the cap is per deployment and the bot shares it. One caveat: an exact repeat is a cache hit whose slot is refunded, so the attacker has to vary the text, which is trivial. The same script reproduced two cheaper variants (see missed): B, five junk 'images' burn all 5 slots for $0 and leave no job or ledger row; C, five concurrent refunded link resolves hold the cap for free and indefinitely. Notes for the fix design: per-IP budgets alone will not hold. A refund pops the per-IP stamp, all Telegram traffic arrives as one client (127.0.0.1), and the multipart routes can be driven from any website (CSRF, see missed). Limit in-flight claims per client as well.

### F2. Under a cloud reverse proxy (shape C) all visitors collapse to one IP for the limiter; the usual FORWARDED_ALLOW_IPS=* fix then makes the per-IP limit fully spoofable
*should-fix · applies to: cloud-host · `app/api/limits.py:118` · tracked: new*

**Scenario.** _client_of reads request.client.host. uvicorn's ProxyHeadersMiddleware is on by default but trusts only 127.0.0.1. Under shape C the TCP peer is a private proxy IP (e.g. 10.x/100.64.x), which is NOT trusted, so X-Forwarded-For is ignored and request.client.host is the proxy IP for EVERY visitor — the per-IP hourly limit becomes a single global bucket. The operator's natural fix, FORWARDED_ALLOW_IPS=* (or a wide CIDR), flips uvicorn to trust-all, where get_trusted_client_address returns the LEFTMOST (client-supplied) XFF value: an attacker then sends a different X-Forwarded-For on each request and gets a fresh per-IP bucket every time, defeating the per-IP limit entirely (spend still bounded only by the global daily cap of F1).

**Evidence.** scratchpad/audit/repro_proxy.py drove the INSTALLED uvicorn/middleware/proxy_headers.py directly. Shape C (peer 10.0.0.7, default trust): two different visitors both resolved to '10.0.0.7'. FORWARDED_ALLOW_IPS=* : XFF '9.9.9.9'->9.9.9.9, '8.8.8.8'->8.8.8.8, '7.7.7.7, 10.0.0.7'->7.7.7.7 (leftmost, attacker-controlled). Note: shape H is SAFE — with peer=127.0.0.1 and Cloudflare appending the real IP as the rightmost XFF entry, a spoofed 'XFF: 1.2.3.4' still resolved to the real 203.0.113.9.

**Fix.** Decide the IP source explicitly for the chosen deployment: on a trusted proxy, trust exactly that proxy's IP/CIDR and read the client from the correct XFF position (or CF-Connecting-IP), never '*'. Add a test pinning _client_of under both shapes so a deploy env var cannot silently make it spoofable.

**Verifier: reproduced.** Reproduced end to end (sv/v_f2.py). uvicorn 0.51.0's own Config(app) gives proxy_headers=True and forwarded_allow_ips='127.0.0.1', and wraps the app in ProxyHeadersMiddleware. I drove that middleware, the real /verify/text route and the real limiter, with the hourly cap lowered to 2 only so the bucket shows. Shape H (peer 127.0.0.1, Cloudflare appends the real IP): distinct visitors got 202, and an attacker rotating a spoofed leading XFF was still refused on its 3rd request (429), so H is safe. Shape C (peer 10.0.0.7, default trust): the 3rd visitor got 429 on its first-ever request, because everyone shares the proxy's bucket. C plus FORWARDED_ALLOW_IPS='*': 5 of 5 rotating-XFF requests got 202, because the leftmost, client-supplied XFF is trusted, so the IP is fully spoofable. C plus '10.0.0.0/8': refused correctly on the 3rd request. Today the per-IP limit (10/h) never binds before the 5/day cap, so the practical effect starts once 11.A raises the cap. should-fix is right.

### F3. FastAPI interactive docs and OpenAPI schema are served publicly (/docs, /redoc, /openapi.json)
*should-fix → **nice-to-have** (verifier) · applies to: both · `app/main.py:144` · tracked: new*

**Scenario.** The FastAPI app is constructed with no docs_url/redoc_url/openapi_url override, so once the app is on any public URL, strangers get the full interactive API explorer and machine-readable schema of the verify endpoints — a ready-made script surface that makes the F1 griefing (and any future auth-bypass probing) trivial to automate.

**Evidence.** scratchpad/audit/repro_app.py (Starlette TestClient against the live app): GET /openapi.json->200, /docs->200, /redoc->200. The local-only admin routes are correctly hidden (include_in_schema=False): '/dashboard' and '/api/v1/admin/spend' are NOT in the advertised paths.

**Fix.** Pass docs_url=None, redoc_url=None, openapi_url=None to FastAPI() for the public deployment (or gate them behind the same local-only check as the dashboard).

**Verifier: reproduced.** Reproduced on real uvicorn on a random 127.0.0.1 port (sv/v_app.py): /openapi.json, /docs and /redoc all return 200, and /docs and /redoc load JS from cdn.jsdelivr.net. But the schema lists only the 7 public paths that the page's own JS already calls; /dashboard and /api/v1/admin/spend are correctly hidden. There is no auth to probe, and F1 needs only 5 curl calls with or without the docs. The page gives an attacker almost nothing new, so turning the docs off is hygiene, not pre-launch work.

### F4. No auth or rate limit on read/stream routes, and no concurrency cap — request/SSE-connection flood DoS
*should-fix · applies to: both · `app/api/stream.py:155` · tracked: new*

**Scenario.** Only the four /verify/* routes go through _quota; /reports/{id}, /stream/{id}, /health, /openapi.json and all static assets have no rate limiting at all, and uvicorn runs with limit_concurrency defaulting to None (unlimited). A stranger can open unbounded concurrent SSE connections (each /stream follower is a long-lived task plus a waiter future appended to the JobStream, with 15s heartbeats) or simply flood the unmetered GET routes, exhausting memory/file-descriptors/CPU on the single worker. Under shape H this takes down the owner's home PC; the in-memory stream registry growth itself is bounded by the daily cap, but concurrent connections are not.

**Evidence.** Read of app/main.py (only middleware is LimitUploadSize; no rate-limit/concurrency middleware), app/api/stream.py follow()/_wait() (one task + one _waiters future per connection, no per-IP connection cap), and .venv uvicorn/config.py (limit_concurrency default None). repro_app.py confirmed /reports and /stream answer with no auth challenge.

**Fix.** Set uvicorn --limit-concurrency and reasonable timeouts; add a lightweight per-IP connection/request cap in front (or at the proxy) covering ALL routes, not just /verify/*; cap concurrent SSE followers per job and per IP.

**Verifier: confirmed-by-reading.** I ran the preconditions but did not cause an outage (sv/v_app.py, real uvicorn). 300 GET /api/v1/reports/<random> from one client took 2.8 s: 300 x 404, never a 429. 300 concurrent SSE connections from ONE client to one live job were all accepted, with 300 waiters parked on the stream. uvicorn.Config's default limit_concurrency is None. The finding is narrower than stated in two ways. First, an SSE connection only stays open on a LIVE job: an unknown id returns 404 and a finished job replays then closes, so holding many connections needs the attacker's own in-flight check. Second, the stream registry is not bounded by the daily cap: a cache-hit job's slot is refunded, so the real bound is the per-IP hourly limit. Each /reports hit is a to_thread SQLite read on asyncio's default pool, which link resolves also use (§11 8), so a flood slows everyone. This is plain volume with no amplification (contrast F5), so should-fix stands. Mitigate with a Cloudflare rate-limit rule plus --limit-concurrency.

### F5. JSON text/link routes accept up to 25 MB bodies, parsed and regex-scanned before the quota is claimed
*should-fix → **blocker** (verifier) · applies to: both · `app/main.py:59` · tracked: new*

**Scenario.** LimitUploadSize uses settings.max_media_bytes (25 MB) as the body cap for EVERY route, including the JSON /verify/text and /verify/link. VerifyTextRequest.text has only min_length=1, no max_length (schemas.py:20); the max_input_chars=5000 check runs only AFTER FastAPI has read and JSON-parsed the whole body, and verify_text even runs nothing_to_check(req.text) (a regex scan over the full string) BEFORE 'async with _quota' (routes.py:259-261). So an unauthenticated 25 MB POST is fully buffered, parsed into a Python str and regex-scanned before any limit applies — repeat concurrently for a memory/CPU DoS on the single worker (worst under shape H).

**Evidence.** Read of app/main.py:59 (limit = settings.max_media_bytes, shared by all http scopes), app/api/schemas.py:20 (text field: min_length=1, no max_length), app/api/routes.py:259-261 (nothing_to_check then _quota). config.py max_media_bytes=26214400.

**Fix.** Give JSON routes their own small body cap (e.g. a few KB, derived from max_input_chars) separate from the media cap, and/or add max_length to the text/url schema fields so pydantic rejects before the route body logic runs.

**Verifier: reproduced.** Reproduced, and worse than described (sv/v_f5.py, sv/v_f5_steps.py). nothing_to_check() is more than a regex scan. It runs a per-character unicodedata loop and then the squeeze r'(.)\1{2,}', synchronously ON the event loop and before _quota. So no cap, refusal or per-IP limit applies, even once the day's cap is used up. Measured directly: 25 MB of one repeated letter took 18.8 s CPU with about 2.2 GB peak allocation. The squeeze alone was 19.3 s / 2.2 GB (sre backtracking state over one long run); the per-character loop was 3.6–7.6 s / 255 MB. 8.4M Devanagari characters (25 MB on the wire) took 4.2 s / 740 MB. On real uvicorn on a random port, one 25.2 MB POST /verify/text got past LimitUploadSize and ended in the route's own 413 ('That message is 25165824 characters'). Its slot was claimed then refunded (used_today=0), and /health was frozen for 10.1 s (3.7 s for the Devanagari body). One stranger uploading about 2.5 MB/s can keep the single worker frozen: the page, every SSE stream and the bot's polling. Each request also adds about 2 GB on the host, which under H is the owner's PC. That is 'cheaply lock everyone out', so blocker. Fix: a small body cap for the JSON routes, max_length on the schema fields (pydantic then rejects before the route body runs), the length check before triage, and a linear-time squeeze.

### F6. No security headers (CSP, X-Content-Type-Options, Referrer-Policy, X-Frame-Options/frame-ancestors) on the page or API
*should-fix → **nice-to-have** (verifier) · applies to: both · `app/main.py:144` · tracked: new*

**Scenario.** static/index.html is served with no Content-Security-Policy, X-Content-Type-Options: nosniff, Referrer-Policy, or framing restriction, and uvicorn emits a Server header by default. The page's own XSS defenses are actually strong (esc(), the restricted md() subset, safeUrl() blocking non-http(s) hrefs, rel=noopener noreferrer on source links), so this is defense-in-depth rather than an active XSS — but without a CSP any future innerHTML regression becomes exploitable, the page can be framed for clickjacking, and there is no nosniff. Low standalone impact, standard pre-public hardening.

**Evidence.** grep across app/ and static/ found no content-security-policy / x-content-type / referrer-policy / x-frame-options / strict-transport. repro_app.py /health response headers were only content-length and content-type. Reviewed static/index.html: esc()/md()/safeUrl() are applied consistently to all innerHTML sinks.

**Fix.** Add a small response-header middleware (or set headers at the proxy) with a strict CSP for the page (self; no inline if feasible, or a nonce), X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, frame-ancestors 'none'; set uvicorn server_header=False.

**Verifier: reproduced.** Reproduced on real uvicorn: /, /api/v1/reports/x and /health send no CSP, nosniff, Referrer-Policy or X-Frame-Options; the only such header is 'server: uvicorn'. The impact is defense-in-depth only. Every innerHTML sink in static/index.html goes through esc(), md() or safeUrl(). safeUrl's p.href cannot contain a raw quote. drawFooter interpolates confidence and tier without escaping, but the API model types them as int and Literal. The page loads no third-party resources and sets no cookies; localStorage holds only the reply language. Source links carry noreferrer, and the job id lives in the URL fragment, which is never sent as Referer. Framing or sniffing has nothing to steal. A strict CSP would need a nonce for the inline script, and /docs loads jsdelivr.

### F7. Subtitle fetch bypasses the SSRF allowlist and follows redirects (host never re-validated)
*should-fix → **nice-to-have** (verifier) · applies to: both · `app/providers/links.py:325` · tracked: new*

**Scenario.** The link module's stated SSRF discipline is that allowed_link_host fails closed on every URL the server fetches. subtitle_text() violates it: it does httpx.get(ref.url, follow_redirects=True) with NO allowed_link_host(ref.url) check, where ref.url is a caption-track URL taken from yt-dlp's resolved metadata. If that URL's host (or a redirect target) points at a private/LAN address, the server will fetch it — under shape H that reaches the home LAN. Exploitability is limited because ref.url originates from the pinned Instagram/YouTube/Facebook extractors rather than free-form user input, but the fetch is unguarded and redirects are followed blindly, unlike the download path (links.py:353 re-checks allowed_link_host).

**Evidence.** Read of app/providers/links.py:321-336 (subtitle_text: httpx.get(ref.url, ..., follow_redirects=True), no host check) vs download_link_audio:353 which does re-check allowed_link_host. The module docstring (lines 22-28) claims every fetched URL goes through the fail-closed host check.

**Fix.** Validate ref.url's host before fetching (reuse strict_host against an allowlist of the platforms' caption CDNs), and either disable redirect following or re-validate each redirect hop's host; optionally resolve-and-pin the IP to a public range.

**Verifier: reproduced.** The behaviour of the function itself is real (sv/v_f7.py). subtitle_text(SubtitleRef(url='http://127.0.0.1:<port>/start')) fetched plain-http loopback, followed the 302 to /internal-admin/secret.vtt and returned its text, while allowed_link_host() returns None for that URL. It is not attacker-reachable as described. ref.url is the platform's own data: YouTube's captionTracks[].baseUrl from the player response, and Facebook's captions_url from its page JSON (yt_dlp/extractor/youtube/_video.py:4260, facebook.py:665-680). Neither the uploader nor the submitter chooses the host. The contrast with the download path is also wrong: links.py:353 re-checks only the PAGE url. yt-dlp then fetches CDN media URLs (googlevideo, fbcdn, cdninstagram, none of them in ALLOWED_HOSTS) and follows their redirects unchecked, which is the same trust model. The fence that matters holds: _base_opts() loads exactly 3 extractors (Facebook, Instagram, Youtube) and generic is absent. yt-dlp fullmatches allowed_extractors, which is stricter than the code comment's 'prefix' claim. No LAN exposure today, so this is defense-in-depth; a caption-host allowlist plus follow_redirects=False is cheap.

### F8. No authorization on /reports/{id} and /stream/{id}; a leaked job_id exposes the sender's full message and answer
*nice-to-have · applies to: both · `app/api/routes.py:551` · tracked: new*

**Scenario.** get_report and stream_answer return the stored Answer (input_text, machine-read source_text, prose, sources, confidence) to anyone who presents a job_id, with no auth. Job ids are uuid4().hex (122 bits of randomness), so they are not enumerable or guessable; the residual risk is that if an id leaks — shared chat link, proxy/access logs, a future referer — the forwarded message (possibly private) and its answer are readable by a stranger. Because ids are strong this is a low-likelihood confidentiality gap, not an enumeration hole.

**Evidence.** Read of app/api/routes.py:551-556 (get_report: no auth) and app/api/stream.py:155-189. repro_app.py: GET /api/v1/reports/<unknown> and /api/v1/stream/<unknown> return 404 with no auth challenge (404 only because the id does not exist). job_id is uuid4().hex (routes.py _new_job).

**Fix.** Acceptable to ship on id-unguessability for now; if messages are treated as private, bind a report to its submitter (signed cookie/token issued with the 202) and/or shorten retention. Keep ids out of any server-side access log.

**Verifier: reproduced.** Reproduced (sv/v_app.py): a stranger holding only a stored report's id got 200 with input_text 'PRIVATE forward from my family group: ...'. Ids are uuid4().hex (122 bits) and cannot be enumerated, and no route lists jobs. The page keeps the id in the URL fragment, so it is never sent as Referer. It does appear in request paths, so it lands in uvicorn's console log and in Cloudflare or platform logs, which only the owner sees. I also checked the static mount for a way out: 12 raw-socket traversal paths on Windows (../, %2e%2e, %5c, a backslash, ::$DATA, a drive path, UNC) all returned 404 for README.md. nice-to-have is right.

### F9. Telegram bot answers anyone who finds it; every check comes out of the shared 5/day cap
*should-fix → **blocker** (verifier) · applies to: both · `scripts/telegram_bot.py:583` · tracked: 11.18*

**Scenario.** @Information_Verifier_bot has no user allow-list: anyone who discovers the username can send checks, and each one draws on the same deployment-wide 5/day cap (F1), so a stranger can both consume the owner's paid budget and lock out the web page. classify_message/handle_message gate on message TYPE, never on the sender's Telegram user id.

**Evidence.** grep of scripts/telegram_bot.py for allow-list/owner/user_id/from.id gating found only the unrelated link-host 'allowlist' comment (line 84); handle_message (line 583) and the Dispatcher never check chat/user id against an allow-list. Matches PROJECT_PLAN §11 18.

**Fix.** Add an owner/allow-list of Telegram user ids in .env, checked before any submit, with a polite refusal for others (as §11 18 proposes). Small and free; do before inviting anyone.

**Verifier: reproduced.** Reproduced with the real handle_message and stub API and Telegram clients (sv/v_bot.py). Messages from three unknown private chats AND a channel post (update.channel_post is handled too) produced 4 submitted checks. Settings has no allow-list field. I raised the severity because the bot needs no public URL: any Telegram user can reach it whenever start.cmd is running. 5 messages, or one channel the bot gets added to, lock both the web page and the bot out for the day. That is exactly F1's blocker impact, and §11 A itself lists §11 18 under 'Before any public URL'. Also, every bot submission reaches the API as one client (127.0.0.1, no X-Forwarded-For), so the API's per-IP limit counts all Telegram users as one visitor. Per-user limits have to live in the bot, keyed by chat or user id.

### F10. Under shape C the owner cannot reach the dashboard, and a loopback-colocated proxy that omits proxy headers could expose it
*nice-to-have · applies to: cloud-host · `app/api/dashboard.py:48` · tracked: new*

**Scenario.** _local_only requires peer in {127.0.0.1,::1}, no proxy headers, and exactly one local Host header. Under shape C the peer is the platform proxy IP, so /dashboard and /api/v1/admin/spend always 404 for the owner too — there is no built-in authenticated way to view spend remotely (owner must SSH/port-forward). Conversely, if a cloud platform fronts the app with a sidecar proxy that connects over 127.0.0.1 AND forwards a request without adding any of the six recognised proxy headers, the gate would open the owner's spend data to that path. The gate is sound under shape H (verified).

**Evidence.** Read of app/api/dashboard.py:39-59. repro_app.py: /dashboard and /api/v1/admin/spend return 404 for a non-local peer even with Host=127.0.0.1:8000, confirming the gate keys on the peer. The _PROXY_HEADERS list is the only thing distinguishing a real local request from a proxied one on loopback.

**Fix.** For a cloud deployment, serve the dashboard over a separate authenticated channel (owner login, or bind it to a localhost-only admin port reached via SSH tunnel) rather than the IP/header heuristic; document that /dashboard is unreachable via the public URL under shape C.

**Verifier: reproduced.** Reproduced on real uvicorn from a real 127.0.0.1 TCP peer (sv/v_app.py). The owner's browser got 200. A cloudflared-style request (CF-Connecting-IP plus XFF) got 404. A proxy that keeps the public Host and adds no headers also got 404: the colleague's condition misses the Host check, so a sidecar that preserves Host stays closed. The real hole is a proxy that rewrites Host to its loopback upstream AND adds no forwarding header. Those are nginx's defaults for a minimal `proxy_pass http://127.0.0.1:8000;` (Host 127.0.0.1:8000, no XFF). With that request shape, /dashboard returned 200 and /api/v1/admin/spend returned 200 with cap, totals and recent spend, for any internet visitor. That is the '₹400–800/month VPS' option in §11 A, where the plan's line 'the dashboard already 404s for anyone but this machine' would be false (a blocker in that shape). Under H and C as defined the gate holds; under C it is closed for the owner too. nice-to-have stands.

### F11. Settings repr/str/dump exposing API keys (11.17) — verified ALREADY FIXED in the working tree
*nice-to-have · applies to: both · `app/config.py:12` · tracked: 11.17*

**Scenario.** Previously repr(settings) / an assertion display / a traceback with locals would print every API key in full. Recorded per task instruction. Residual: direct attribute access (settings.anthropic_api_key) still returns the plain value by design, so any code that logs that attribute directly would still leak — that class of bug is exactly what the (now-fixed) Telegram token-in-URL log was.

**Evidence.** scratchpad/audit/repro_repr.py: repr(settings) contains none of the five credential values; model_fields['anthropic_api_key'].repr is False. app/config.py:12-32 defines _credential() with repr=False, exclude=True; tests/test_secrets.py pins that every credential-named field is repr=False and exclude=True. (Note: config.py line numbers shifted vs the session-start snapshot because the file is being edited live.)

**Fix.** No code change needed — confirm tests/test_secrets.py passes in the merged result. Optionally add a guard/log-filter for accidental direct logging of a key value.

## Verifier: missed (new findings)

- [blocker, new] Any website can make its visitors' browsers submit PAID checks through the multipart routes /verify/image and /verify/media (cross-site request forgery). The comment at main.py:152-155 says removing the CORS wildcard stops 'any website driv[ing] checks from its visitors' browsers'. That only holds for the JSON routes: FastAPI 0.139's strict_content_type plus the application/json preflight block them. multipart/form-data is CORS-safelisted, so fetch(url,{method:'POST',mode:'no-cors',body:formData}) from any page goes out with no preflight, and the routes never check Origin or Sec-Fetch-Site. Reproduced in real headless Chrome (sv/v_csrf_browser.py): a page on another origin made the browser POST /verify/image. The server reached the (stubbed) paid vision call and the chat check and took a daily slot, while the same page's JSON POST to /verify/text was blocked ('Failed to fetch'). Any site with traffic can drain the cap and the owner's money from its visitors' real IPs, which also defeats the per-visitor budgets that F1's fix relies on. Fix: refuse POSTs whose Origin is present and not the app's own (or Sec-Fetch-Site: cross-site), or require a Turnstile token or custom header on every /verify/* route.
- [blocker; tracked as §11 14 but mis-assessed] A free, indefinite lockout that leaves no trace, built from in-flight claims that end in a refunded rejection. Five concurrent /verify/link submissions of any long YouTube video (free resolve, then 413 for over-duration, then refunded) hold all 5 daily slots while yt-dlp runs. Afterwards used_today goes back to 0, with no job or ledger row and $0 spent. refund() also pops the per-IP stamp, so the attacker never reaches the 10/h limit. The same works through /verify/media, where ffprobe/ffmpeg failures after up to 120 s each are refunded. The unthrottled resolves also hammer YouTube, Instagram and Facebook from the server's IP (under H, the owner's home IP), inviting platform rate limits for everyone. Fix: cap in-flight claims per client (for example 1), stop a refund from erasing the per-client stamp, and do not tell people 'try tomorrow' when slots are only held.
- [should-fix, new] F1's lockout can cost $0 and leave no record. verify_image calls spend.begin() BEFORE the vision call, so when that call raises (junk bytes labelled image/png get an unbilled Anthropic 400), the slot is kept, the client gets a bare 500, and no job row or spend_ledger row is written.
